Usage, Plugin and Theme Guide

Install YDevDesk in minutes, speed up your workspace with keyboard shortcuts, set up the shared memory of your agents (Knowledge Network), and build your own plugins, themes or core modules.

Installation (Linux / macOS / Windows)

YDevDesk is a native desktop application built on Tauri v2 and a Rust core. It runs without installing any external runtime (Node.js or Electron).

Linux (Recommended One-Liner)

Automatically installs the latest release on Arch, CachyOS, Ubuntu, Debian, Fedora and other modern Linux distributions:

bash — One-Command Install 
curl -fsSL https://raw.githubusercontent.com/YagYz/YDevDesk/main/install.sh | bash

Ubuntu / Debian (APT Repository)

Add the APT repository to receive updates through the standard apt upgrade flow:

bash — APT Install 
echo 'deb [trusted=yes] https://yagyz.github.io/YDevDesk/apt ./' | sudo tee /etc/apt/sources.list.d/ydevdesk.list
sudo apt update && sudo apt install -y ydevdesk
Linux Wayland & NVIDIA Note

The install.sh script automatically installs a wrapper that sets the WEBKIT_DISABLE_DMABUF_RENDERER=1 environment variable to avoid the WebKitGTK white-screen issue on Wayland + NVIDIA GPUs. If you launch the AppImage manually, you can prepend this variable to the command.

macOS (Apple Silicon & Intel)

Download the .dmg package matching your processor (aarch64.dmg or x64.dmg) from the GitHub Releases page, drag the app into /Applications, and remove the quarantine attribute before the first launch:

zsh — macOS First-Run Permission 
xattr -cr /Applications/ydevdesk.app

Windows (64-bit)

Download and run the *-setup.exe (NSIS) installer from the latest release. When setup finishes, a YDevDesk shortcut is available in the Start menu.

First Launch & Connections

On first launch, YDevDesk automatically detects the AI coding agents installed on your computer (agy, claude, codex). You can personalize your environment with the following steps:

  • Project Root Directories: In Settings → Connections, add the project folders you work in often (for example /mnt/Depo/Projeler or ~/Projects). Git status, the file map and quick terminal launching use these directories.
  • Homelab Services (Optional): If you use YDevHub or YNetMon, add the URL and API key to enable the notes, tasks, Knowledge Network and live network traffic panels.
  • Agent Memory (Knowledge Network): So that your agents can see each other's work, look at the Settings → Knowledge Network tab; details are in the Knowledge Network section.
  • Optional Sync: If you work on more than one computer, you can turn on encrypted GitHub Secret Gist sync (Turkish page) from the Settings → Sync tab.

Settings Tabs

The Settings window has these tabs: Connections, Modules, Themes, Plugins, Commands, Notifications, Agents, Knowledge Network, Sync and Version.

Built-in Panels (Modules)

Built-in panels you can add to the workspace: Sessions, Agent Status, Tool Feed, Git, File Heat, Quick Actions, Tasks, Notes, Knowledge Network and YNetMon Network. The Tasks, Notes and YNetMon Network panels need a YDevHub / YNetMon connection; you can choose which panels are shown in Settings → Modules.

Keyboard Shortcuts

The Dockview workspace and the quick command palette are designed for keyboard-first use:

Shortcut Action Description
Ctrl + K (Cmd + K also works on macOS) Command Palette (Omnibar) Switch between three modes with Tab: send a command to the terminal, quick note (when YDevHub is connected) and Memory (add an entry to the Knowledge Network). Esc closes it.
Ctrl + Tab Panel / Tab Switching Instantly switches between open Dockview tabs and terminals.
Ctrl + Shift + T (Cmd also works on macOS) Reopen Closed Panel Restores the last terminal or tool panel you closed by accident, with its layout.

Terminal & Click-to-Cursor

YDevDesk uses a native Rust PTY (portable-pty) and a high-performance terminal renderer. Compared with classic desktop terminals, you can run several shell sessions side by side with much lower memory use.

  • Click-to-Cursor: While editing a long bash/zsh command, instead of holding down the arrow keys you can click any character on the command line to move the cursor straight there.
  • Terminal Presets: Save frequently used SSH connections, agent launchers or project scripts as presets and open them in a new tab with one click.
  • Theme Matching: When you change the application theme, the background, foreground, cursor and selection colors of all open terminals update instantly.

Markdown Auto-Open & Open File

AI agents often produce plan files, technical reports or documents. YDevDesk's built-in Markdown Viewer panel presents these files readably in the center of your workspace:

  • Auto-Open: View .md files created or updated in agent output or in the File Heat panel in a new tab with one click or through automatic watching.
  • Open File: Open any Markdown file on your computer instantly from the top toolbar or from the plugin/module SDK (openMarkdown).
  • Live Refresh: The content refreshes automatically when the file changes on disk.

AGY, Claude Code & Codex Agents

YDevDesk brings the three major coding agents running on your local machine into a single interface:

  • Antigravity (AGY): Reads conversations, session IDs and token usage under ~/.gemini/antigravity-cli/.
  • Claude Code: Lists the session history and per-project chats under ~/.claude/.
  • OpenAI Codex: Detects session records under ~/.codex/ and lets you continue with one click.

In the Sessions panel you can pin any conversation, give it a custom alias, and resume where you left off in the built-in terminal with one click, using the agent's --resume command.

The Settings → Agents tab scans the installed agents; it lets you launch them in normal or bypass mode, update them, open them in a terminal and install missing ones. To let agents see each other's work, use the Knowledge Network memory.

Safe Session Deletion

You can clean up old agent sessions you no longer need directly from YDevDesk. The safe session deletion mechanism:

  • Asks for explicit confirmation before deleting, preventing accidental data loss.
  • Removes only files inside the verified (path-validated / canonicalized) session directory of the relevant agent; it never touches system or project files.
  • Automatically cleans up pin and custom-name records as well.

Quota & Cost Tracking

The analytics panel derives detailed usage from local session logs over 1-day, 7-day and 30-day windows, without any external plugin or cloud tool:

  • Tokens & USD Cost: Shows input, output and cache token counts together with an estimated per-model USD cost.
  • Quota Thresholds: Tracks 5-hour and weekly usage quotas with live progress bars; when your chosen threshold is reached it gives a local desktop notification and an audible alert.
  • Multi-Device Total: If encrypted Gist sync is on, usage summaries from all your devices are merged into a single chart.

Knowledge Network: What It Is and How It Works

Detailed guide

Which files change on your system, backups, manual install and manual removal, privacy and data flow: Detailed guide → knowledge-en.html

The Knowledge Network is a local memory shared by your Claude Code, Codex and Antigravity (AGY) sessions. When an agent finishes its work it writes a short entry about what it did; in the next session (the same or a different agent) it reads these entries before starting, so it can see where things were left. That way it does not repeat work or undo earlier work.

  • Local SQLite: Entries are kept in a SQLite database (WAL mode) on your computer. The default location is com.yagyz.ydevdesk/knowledge.db under the operating system's data directory. You can set a custom absolute path (or one starting with ~/) in Settings → Knowledge Network → Database path; relative paths are rejected because they would make different processes write to different databases.
  • Entry fields: service (project name), title, summary, tags, device name and the writing agent (claude, codex, agy, user or unknown). The agent name is an unverified claim.
  • Tags: Tags written inside the summary as [[service/topic]] are parsed automatically; you can also pass extra tags through the tags field.
  • YDevHub is optional: If you have YDevHub in your homelab, entries can be mirrored there too. Without YDevHub the Knowledge Network works fully locally.
  • Agent access (MCP): Agents reach the memory through a stdio MCP server started with ydevdesk --mcp, which opens no window. The same service layer is used by the application UI.
  • In the UI: The Knowledge Network panel lists entries; in the Ctrl + K command palette you can add an entry by hand with the Memory mode (service name Hızlı Kayıt, agent user). Settings are in the Settings → Knowledge Network tab.

Storage Modes

There are three modes under Settings → Knowledge Network → Storage. The default is Local. If the YDevHub connection (Settings → Connections) is not configured, the other two options cannot be selected.

ModeWriteRead
Local Only the SQLite database on this device. The local database.
YDevHub Only YDevHub. If the hub is unreachable the entry is placed in the local send queue (outbox). Directly from YDevHub. If the hub is unreachable, reading fails; it does not fall back to the local database.
Both First to the local database, then to YDevHub. If the hub is unreachable the entry still stays local and is queued for the hub. The local database.

Queue while the hub is down

  • Entries that could not be sent wait in the outbox table of the local database. While the app is open the queue is drained every 30 seconds, and also in the background after each successful MCP write; at most 20 entries are processed at a time.
  • On a transient error (network, 5xx, 408, 429) entries stay in the queue and are retried later. An entry that gets a permanent error (other 4xx) is skipped and does not block the ones after it; an entry whose attempt count reaches the upper limit is no longer retried and stays in the queue.
  • Delivery is at-least-once: in rare cases where a response is lost, the same entry can reach the hub twice.
  • With the Off run permission, the background drain does not go to the network either.
  • The status line under the settings tab shows the number of entries and the number of entries in the queue.

Run Permission

Settings → Knowledge Network → Run permission decides whether agents can use the MCP tools:

OptionBehavior
OffThe MCP tools reply knowledge devre dışı (kapalı) (disabled, off). The background queue drain does not run either.
Only while the app is openThe tools work while YDevDesk is running. The app refreshes the app.alive heartbeat file every 5 seconds; a heartbeat that is missing or older than 15 seconds means "app closed", and the tools reply knowledge devre dışı (uygulama kapalı) (disabled, app closed).
Always (default)The tools work even when the app is closed.
The MCP server is not a daemon

ydevdesk --mcp does not run as a background service; the agent starts it when an agent session opens and it exits with the session. "Always" does not mean the server runs all the time; it only means the app does not have to be open when the agent starts it. The panel and Quick Entry in the application UI are managed by the user, so they are not subject to this gate.

If the settings file is corrupt, it stays off

Settings are kept in ~/.config/ydevdesk/knowledge.json. If the file does not exist the defaults are used; if it exists but cannot be read or parsed, the feature stays on the safe side: the run permission is treated as Off. Fix or delete the file.

MCP Tools

The server is registered as ydevdesk-knowledge (stdio, JSON-RPC 2.0) and offers two tools. Tool descriptions and response texts are in Turkish.

knowledge_log

Records finished work in memory. Called when a task is done.

FieldTypeDescription
servicestring, requiredService or project name (at most 100 characters, no control characters).
titlestring, requiredShort single-line title (at most 200 characters).
summarystring, requiredA one-to-two sentence summary; may contain [[service/topic]] tags (at most 8000 characters).
tagsarray of strings, optionalExtra tags (at most 20, each at most 64 characters; cannot contain [ or ]).

On success it returns kaydedildi #<id> ("saved"); if the entry was put into the hub queue, (hub kuyruğunda) ("in hub queue") is appended.

knowledge_read

Reads recent entries. Called for the relevant service before starting work. All fields are optional.

FieldTypeDescription
servicestringFilters by service/project name.
searchstringText search (case-insensitive).
tagstringFilters by tag.
limitintegerDefault 10, at most 100.
  • The output is wrapped in a leading "untrusted data" warning and in <knowledge_entries> delimiters carrying a random nonce on every call; entry content cannot imitate this boundary.
  • Each entry is listed with service, id, title, agent@device, UTC time and the word "doğrulanmamış" (unverified). Control characters are stripped; a single entry summary is limited to 2000 characters and the total output to roughly 20,000 characters. If the limit is exceeded, the output says how many entries were not shown.
  • If there are no entries it returns kayıt yok ("no entries").

One-Click Setup from the App

Detailed guide → which files change

The Settings → Knowledge Network → Add to agents section does two things for you for Claude Code, Codex and AGY:

  1. MCP registration: Adds the ydevdesk-knowledge server to the agent's user (global) configuration, with the app's own binary as the command and --mcp as the argument.
  2. Global rules file block: Adds an English rule block to the agent's global rules file, between the <!-- ydevdesk:knowledge:start --> and <!-- ydevdesk:knowledge:end --> markers (it tells the agent to call knowledge_read when starting work and knowledge_log when finishing).

How it proceeds

Tick the agents and press Preview and add; the target paths, the action and the snippet to be written are shown in the preview, and no file changes until you press Confirm and write. Only the marked block is written, a <file>.ydevdesk.bak backup is made before the first write, writes are atomic, and a second click does not duplicate anything. Remove undoes what was added. For the step-by-step flow, error cases and manual removal see the detailed guide.

AgentMCP registrationGlobal rules file
Claude Codeclaude mcp add --scope user~/.claude/CLAUDE.md
CodexA marked [mcp_servers.ydevdesk-knowledge] table in ~/.codex/config.toml~/.codex/AGENTS.md
AGYMerged into the mcpServers object in ~/.gemini/config/mcp_config.json~/.gemini/config/GEMINI.md (not an officially documented global rules path, but verified against AGY; see Known Limitations)

Manual Setup

Detailed guide → manual install Manual removal

If you do not want to use one-click setup, you can register the MCP server by hand for each agent. In all three examples the command must be the full path of the YDevDesk binary and the argument must be --mcp. To find the path:

  • Linux (install.sh): ~/.local/bin/ydevdesk (the launcher that forwards arguments to the AppImage). If you run the AppImage manually, use the $APPIMAGE path.
  • Linux (APT / .deb): the output of command -v ydevdesk.
  • macOS: /Applications/ydevdesk.app/Contents/MacOS/ydevdesk (adjust if you moved the app elsewhere).
  • Windows: ydevdesk.exe in the install directory; quote the path if it contains spaces.

Claude Code

bash — Claude Code MCP registration 
claude mcp add --scope user ydevdesk-knowledge -- <ydevdesk path> --mcp

Codex

Add this table to ~/.codex/config.toml (using a TOML literal string, that is single quotes, for the path is safe for Windows paths containing backslashes):

~/.codex/config.toml 
[mcp_servers.ydevdesk-knowledge]
command = '<ydevdesk path>'
args = ["--mcp"]

Antigravity (AGY)

Add the entry to the mcpServers object in ~/.gemini/config/mcp_config.json; do not delete the other servers in the file:

~/.gemini/config/mcp_config.json 
{
  "mcpServers": {
    "ydevdesk-knowledge": {
      "command": "<ydevdesk path>",
      "args": ["--mcp"]
    }
  }
}

Restart the agent after registering. To add the rule block as well, use the templates in the next section; without the rule block the tools are available but the agent may not call them on its own.

Rule Template Download Links

The rule block that tells agents when to read and write memory is in English and is provided with identical text in three template files. Each file starts with a short setup note; the block between the markers (ydevdesk:knowledge:start/end) is the managed part: if you paste an updated block again, it replaces the old one.

TemplateWhere to add it
agents/CLAUDE.md Claude Code: append to the end of ~/.claude/CLAUDE.md.
agents/AGENTS.md Codex (and agents that read AGENTS.md): append to the end of ~/.codex/AGENTS.md.
agents/GEMINI.md Antigravity (AGY): add it to ~/.gemini/config/GEMINI.md to apply to every project, or to GEMINI.md in a single project's directory to limit it to that project (one-click setup uses the global path).
bash — Example of appending for Claude Code 
curl -fsSL https://yagyz.github.io/YDevDesk/agents/CLAUDE.md >> ~/.claude/CLAUDE.md

The HTML comment at the top of the template is appended to the file as well; it is harmless. If you add it by hand, you can copy only the block including the markers. Do not add the same block twice; to update, delete the old block and paste the new one.

Security Notes

Detailed guide → security model Privacy & data flow

  • Entries are untrusted data. The text in memory may have been written by other sessions, other agents or data coming through YDevHub. The knowledge_read output is wrapped in a warning and random delimiters, and the rule template tells the agent never to follow instructions found in entries. Still, this is a defense layer, not an absolute guarantee.
  • Do not write secrets. Do not put tokens, passwords, API keys or file contents into entry fields. Entries are stored as plain text in the local database and, in YDevHub mode, are sent to the hub.
  • Run permission is not a security boundary. Any process running as the same user can read and write both the settings file and the database directly. The permission is for managing agents' use of the tools; it does not protect against unauthorized processes.
  • If the settings are corrupt it stays off. A corrupt knowledge.json does not silently turn the feature on; it is treated as Off.
  • File permissions. On Unix systems a new database file is created with 0600 permissions and a new folder with 0700. The permissions of an existing folder are not changed.
  • Hub requests. YDevHub calls are made with the X-API-Key header and redirects are not followed; the key never goes to another address. The timeout is 5 seconds.
  • Setup changes. One-click setup does not write without a preview, makes a backup before writing, and touches only the marked block.

Known Limitations

Detailed guide → known limits

  • The AGY global rules file is not officially documented. One-click setup writes to ~/.gemini/config/GEMINI.md; the path was verified by experiment with a real AGY and depends on the AGY version. Do not put the same block in two places. Details: guide.
  • On Windows and Linux, MCP has been verified only at build/test level. End-to-end use with a real agent has not been tried on these platforms; please report any problems.
  • Queue behavior in hub-only mode. If the hub is unreachable the entry goes only to the local queue, does not appear in the local entry list (knowledge_log returns no entry number in this case) and cannot be read until it reaches the hub. Draining the queue depends on the app (or another MCP call) running.
  • At-least-once delivery. Queueing and hub delivery can produce duplicates; no client-side deduplication is done.
  • The tag filter works differently on the hub. In hub-only mode tag maps to the hub's link parameter (exact match).
  • Deleting or editing entries is not available in the MCP tools; only adding and reading are supported.

Plugin Development

You can extend YDevDesk without compiling its source code. Runtime plugins are written in plain HTML, CSS and JavaScript and run inside a secure sandbox="allow-scripts" iframe.

Folder Layout

Each plugin lives in its own folder. The folder name may contain only letters, digits, - and _:

Folder Layout 
~/.config/ydevdesk/plugins/
└── hello-helper/
    ├── plugin.json     # Plugin manifest and requested permissions
    └── index.html      # Entry point (at most 2 MiB)

Full plugin.json Schema

~/.config/ydevdesk/plugins/hello-helper/plugin.json 
{
  "id": "hello-helper",
  "name": "Quick Helper",
  "version": "1.0.0",
  "description": "Sample runtime plugin: terminal command, notification and local storage.",
  "author": "Your Name",
  "width": 320,
  "entry": "index.html",
  "permissions": ["terminal", "markdown", "notify", "storage"]
}

When you press the Refresh button in the Settings → Plugins tab, your new plugin appears in the panel list immediately.

Complete Working index.html Example

YDevDesk automatically injects all the CSS variables of the active theme (--bg, --surface, --accent, etc.) and the window.YDevDesk bridge into your plugin's <head>.

~/.config/ydevdesk/plugins/hello-helper/index.html 
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8" />
  <style>
    body {
      padding: 14px;
      font-size: 13px;
      background: var(--surface);
      color: var(--txt-main);
    }
    h3 { margin: 0 0 10px; font-size: 15px; }
    .row { display: flex; gap: 8px; flex-wrap: wrap; margin-bottom: 12px; }
    button {
      background: var(--surface-raised);
      color: var(--txt-main);
      border: 1px solid var(--border-glow);
      border-radius: 7px;
      padding: 7px 11px;
      cursor: pointer;
    }
    button:hover { border-color: var(--accent); color: var(--accent); }
    .muted { color: var(--txt-muted); font-size: 12px; }
  </style>
</head>
<body>
  <h3>Quick Helper Plugin</h3>
  <div class="row">
    <button id="btn-git">Run git status</button>
    <button id="btn-notify">Send Notification</button>
    <button id="btn-count">Increment Counter</button>
  </div>
  <p class="muted" id="status">Ready.</p>

  <script>
    const statusEl = document.getElementById("status");

    async function init() {
      const count = await window.YDevDesk.storage.get("clicks", 0);
      statusEl.textContent = "Saved click count: " + count;
    }

    document.getElementById("btn-git").addEventListener("click", async () => {
      await window.YDevDesk.runInTerminal("git status -sb");
      statusEl.textContent = "Command sent to the active terminal.";
    });

    document.getElementById("btn-notify").addEventListener("click", async () => {
      await window.YDevDesk.notify("Quick Helper", "The plugin notification worked!");
    });

    document.getElementById("btn-count").addEventListener("click", async () => {
      const prev = Number(await window.YDevDesk.storage.get("clicks", 0)) || 0;
      const next = prev + 1;
      await window.YDevDesk.storage.set("clicks", next);
      statusEl.textContent = "Saved click count: " + next;
    });

    init();
  </script>
</body>
</html>

Permission Model & window.YDevDesk SDK Reference

Each plugin can call only the capabilities it declares in the permissions array of plugin.json. If a call is made without permission, the bridge rejects the request.

markdown window.YDevDesk.openMarkdown(path, title?) Opens the given local .md file in the central Markdown tab.
notify window.YDevDesk.notify(title, body) Sends an operating system desktop notification.
storage window.YDevDesk.storage.get(key, fallback?)
window.YDevDesk.storage.set(key, value)
window.YDevDesk.storage.remove(key) 		Read, write and delete in an isolated key-value storage area private to the plugin.

Core Module SDK (Source Code Contribution)

If you want to contribute a new built-in panel directly to the YDevDesk repository, you do not need to edit registry.ts, Workspace.tsx or TitleBar.tsx. The src/modules/<id>/manifest.ts file is discovered automatically by Vite.

src/modules/my_module/manifest.ts 
import { Box } from "lucide-react";
import type { ModuleManifest } from "../../sdk/moduleSdk";
import MyPanel from "./MyPanel";

const manifest: ModuleManifest = {
  id: "my_module",
  title: "Module Title",
  description: "Short panel description",
  icon: Box,
  component: MyPanel,
  width: 320,
  order: 100,
};

export default manifest;

Inside your panel component, you can access all core services through the useModuleSDK("my_module") hook:

src/modules/my_module/MyPanel.tsx 
import { useModuleSDK, useVisibilityPoll } from "../../sdk/moduleSdk";

export default function MyPanel() {
  const sdk = useModuleSDK("my_module");

  // Polling that pauses automatically while the window is hidden
  useVisibilityPoll(() => {
    // Periodic data refresh
  }, 15000);

  return (
    <div className="p-3">
      <button onClick={() => sdk.terminal.run("git status")}>
        Check Status
      </button>
    </div>
  );
}
  • sdk.terminal.run(cmd) — Runs a command in the active terminal.
  • sdk.markdown.open({ path, title }) — Opens a Markdown file in the central tab.
  • sdk.notify(title, body) — Sends a desktop notification.
  • sdk.storage.get / set — Isolated local storage private to the module.
  • sdk.connections.projectRoots — The list of project root directories from Settings.

Data & Cache Paths

YDevDesk stores all settings, plugins, custom themes, Knowledge Network entries and encryption keys only on your local disk. Sensitive configuration files are created on Unix systems with 0600 permissions (readable and writable only by the user).
